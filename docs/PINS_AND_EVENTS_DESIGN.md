# 募集ピン・オフ会 詳細設計案 v0.1

2026-10-29。対象R12/R13/R14/R16/R17/R19。要件6章とFigmaを基準に具体化。E01〜E03は承認済み。他の具体方式は設計案。DB・API・画面は未実装。

## 1. 体験と状態を分ける

募集は「今、ここで人と会いたい」という20分の意思表示。イベントは「この日時・場所で会う予定」。イベント参加登録でチェックインや気配を作らない。募集に参加登録・定員・名簿を追加しない。

| 対象 | 状態 | 終了条件 |
| --- | --- | --- |
| 募集 | 作成中（端末）、公開中、終了 | 20分・本人終了・滞在終了／失効 |
| イベント | 作成中（端末）、開催前、開催中、終了、中止 | ends_at到達、主催者中止。終了から復活不可 |
| 参加登録 | 未参加、参加中、取消済み | 本人取消、イベント終了／中止に伴う公開終了 |

送信中・応答不明・失敗は通信状態であり、サーバーの業務状態と混ぜない。満席は参加数と定員から算出する。

## 2. 画面から操作まで

### 募集

Mapの追加→募集タブ→題名→現在地取得→公開する位置の確認→作成。位置は公開時の一点で追従しない。取得失敗なら位置なしで作成せず、入力を保持して再取得。チェックインが切れていればNFC案内を出す。地図を見るだけの現在地ボタンでは公開しない。

サーバーで滞在有効性と同時1件を確認して公開。応答不明なら同じ操作の結果を照会し、新規作成を重ねない。編集できるのは題名。続ける／場所を変える場合は終了して新規作成。旧ピンの終了に成功し新規作成に失敗した場合、終了したピンを勝手に復活させない。募集の閲覧者には名前付き募集という本人の明示的公開を示し、匿名の気配と混同しない。

### イベント

追加→オフ会タブ→題名・日時・定員・説明→場所選択→全画面Map→地点を決定→入力を保持したシート→作成。街へのチェックイン不要。地点は街内。開催中は終了時刻のみ変更でき、開始から24時間以内とする（M01）。

日時は開始・終了の行をタップしてiPhone標準の選択画面を開く。決定で入力へ反映し、キャンセルは元の値を維持する。端末の時刻で表示し、APIにはISO時点を渡す。書式を手入力させる説明ラベルは置かない。作成・編集で共通部品を使い、送信中・未確定送信の復元中は既存の編集ロックを維持する。実装/検証状態はMVP_TASKSを参照。

Map/Homeから詳細シート→内容・開催日時・場所・参加人数／定員を確認→参加。成功後に参加済み表示とHomeへ反映。イベント参加者名は主催者・運営のみ、本人は自身の登録だけ。他参加者には人数のみ。満席でもイベント詳細は閲覧可能。

参加取消は終了まで可能。イベントが開催中でも空席があれば参加可。期限到達・中止はサーバー時刻で判定。詳細を開いた後に満席／中止になったら最新状態を返し、成功と表示しない。

主催者は編集・中止・参加者一覧を操作。中止時は対象イベントを示して確認し、参加者への連絡対象を生成。編集の競合時は最新内容を取得し、入力を保持して差分を見直す。自分の古いフォームで新しい変更を上書きしない。

## 3. データとAPI案

募集：id、visit_id、owner、street、title、公開座標、created_at、expires_at、ended_at/reason、revision。owner/streetは親滞在と一致。期限は作成受理から20分、親滞在の有効性で早期非公開。

イベント：id、host、street、title、description、地点、starts_at、ends_at、capacity、canceled_at、revision。定員は初期20人、1〜100人。無制限なし（M01）。日時は時点として保存し表示で変換。既存の題名50文字・説明1000文字・90日先・24時間・同時3件を適用。

登録：event_id＋account_id一意、joined/canceled、revision。取消行は有効イベント中保持。名簿APIと人数APIを分離し、全名簿を端末へ送ってUIで隠す実装にしない。

論理操作：create/edit/end_recruitment、create/edit/cancel_event、join/cancel_registration、get_event、get_my_upcoming、get_host_roster。変更には操作ID、編集には期待revisionを付ける。主体は認証から取得、サーバーが期限・所有者・制限を検査する。原則本人の作成物だけ変更可能。運営による非公開は別権限の操作。

作成系には有限の受付期限と結果記録が必要。入街の2分を自動流用しない。M02で共通受付10分、結果の最小記録は受付終了後24時間保持と承認。入街の2分は維持する。

## 4. 同時処理

募集はアカウント親→滞在→ピンの順でロック。同時1件・発行頻度・滞在有効性を同じDB処理で判定。退出が先なら作成拒否、作成が先なら退出で終了。

イベント参加・取消・編集・中止は認証主体の資格確認とevent親ロックを統一。Read Committedでロック取得後の別SQLで最新参加数を読む。最後の1席への同時参加は一方だけ成功。定員を現在人数未満へ下げない。参加と取消は登録revisionで古い操作を拒否し、再送で取消を復活させない。対象イベントが不在／終了なら登録を新規生成しない。

操作結果は現在状態とrevision・server_timeを返す。端末は画面操作世代とIDを確認し、遅れた参加成功応答で取消済み表示を戻さない。主催者のログアウトや街からの退出でイベントを自動中止しない。

## 5. 重要変更の通知：合意候補

**E01（承認済み）：開始・終了日時、場所の変更と中止を重要変更とし、アプリ内通知＋プッシュを初期範囲にする案。** 題名・説明のみの変更は詳細で確認可能とし、毎回プッシュしない。通知拒否時もアプリ内で確認できる。メール通知は初期範囲に追加しない。プッシュ内容は「参加予定のイベントに変更があります」等の最小情報とし、名簿や正確な地点をロック画面へ出さない。

**E02（承認済み）：主催者が参加者を個別に取り消す機能はMVPに入れず、問題対応は運営への通報で扱う案。** 現在の主催者一覧は維持。参加者管理に除名・再参加禁止まで含めると権限と通知の追加設計が必要になるため。運営の利用停止時には一般参加登録も自動取消し、解除で復活させない（2026-10-31承認）。主催者自身による個別除名は対象外のまま。

**E03（承認済み）：中止後は参加予定一覧から外し、アプリ内通知で中止を知らせる案。** 中止通知は中止から24時間以内だけ保持し、その後参加者との対応を消す。過去参加履歴は作らない。24時間以内にアプリを開かずプッシュも届かなかった場合、中止連絡を見逃し得る。通知を長く残す場合は既存の参加関係削除方針との調整が必要。

## 6. 通知と削除の整合案

変更のDB処理と同時に、イベント版・宛先・種類を最小限のoutboxへ登録。外部送信はコミット後に行い、失敗でイベント変更を巻き戻さない。外部通知は完全な一回配信を保証しない。通知IDで端末の重複表示を抑え、古い版の通知が届いても詳細は最新状態を取得する。

送信前に利用資格・参加状態・現在イベント状態を再確認。取消した人へ未送信の変更通知は送らない。中止前の変更通知が未送信なら中止通知へ整理し、古い日時の変更を後から送らない。参加登録と通知宛先は終了／中止から24時間以内に削除、削除後の再試行で再生成しない。中止通知の表示は承認済みE03に従って具体化。本文・地点は終了後取得対象外の既存方針を守り、終了後に通知から古い詳細を無制限に開ける設計にしない。

取消・期限・削除は公開取得時にも判定し、ジョブ待ちでピンや参加状態が残らないようにする。通報証拠は別権限・別期限。運営によるイベント非公開・主催者利用停止時の扱いは運営設計で決める。
