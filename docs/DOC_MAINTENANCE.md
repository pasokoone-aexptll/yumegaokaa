# docsの更新と実装レビュー

## 全体進捗の更新（2026-10-30）

作業前に[MVP_TASKS](MVP_TASKS.md)の対象T番号とR番号を確認する。完了時はTODO/IN_PROGRESS/BLOCKED/IMPLEMENTED/DONEの5状態で更新し、完了条件とコード・検証の証拠、残作業を記録する。モック・未接続・未確認を完成にしない。分母の追加・削除・分割・統合は理由と率への影響を残す。率はDONE/全件、実装到達率は(DONE+IMPLEMENTED)/全件で再集計する。

報告は「MVP開発進捗」として実装済み・統合確認済み・iPhone実機確認済み・DONE・BLOCKEDの件数/33と率を示す。従来の作業ステータスは維持し、達成段階は別列で管理。今回実際に使えるようになった機能、DONE未達の具体理由、次の作業を記す。実機不要のバックエンドは対象外と明記し、実機率へ加算しない。部分成功やインストール成功を対象機能全体の実機確認に置き換えない。検証不足をコード不足と混同せず、追加の細部テストより全画面の実データ統合と実機一巡を優先する。

更新：2026-10-29。ユーザーの「docsを開発・整合性評価の基準にする」依頼を作業手順に落としたもの。

## 作業を始めるとき

1. [入口](README.md)、[要件](MVP_REQUIREMENTS.md)、該当する[確認条件](ACCEPTANCE.md)、[未決定事項](OPEN_QUESTIONS.md)と[実装状況](TECH_VALIDATION.md)を読む。
2. 作業対象のR番号、採用済み要件、未承認の方式、実装の差分を特定する。構成案や過去コードを仕様に昇格させない。
3. 現在のユーザー指示に訂正があれば先に文書へ反映する。記憶だけで以前の案を実装しない。

## 決定が変わったとき

- DECISIONSに日付・ユーザー発言の根拠・置き換えた旧判断を記録する。
- 要件の該当箇所を置換し、未決定一覧から解決した項目を除く。末尾に「最新」を足して相反する本文を放置しない。
- 画面・方式案・確認条件・実装状況に影響する箇所も同じ作業で更新する。
- 大きな整理では旧版をhistoryに残す。既存の原資料は書き換えない。
- 文書更新とコード変更を区別する。仕様が変わってもコード未反映なら差分として明記する。

## 仕様で問題を解けないとき

既存要件に適合する実装上の修正は進めてよい。一方、機能範囲・公開範囲・保持期限・本人の意思・製品の振る舞いを変更する必要がある場合は、次を記録してユーザーに判断を求める。

- 該当R番号と再現条件／証拠。
- 現行仕様では何が成立しないか。実装不具合か、仕様の不足か、OS制約か。
- 代替案ごとの体験、保存情報、工数、運用への影響。
- 推奨案と承認が必要な点。承認前はOPEN_QUESTIONSまたは提案文書へ置く。

未決定事項を独断で確定したり、テストを通すために要件を弱めたりしない。影響のない作業は継続する。定型的な内部実装の選択まで毎回承認待ちにする必要はない。

## 作業の完了時

- 関連R番号について仕様との差分をレビューし、コード/テスト/実機の証拠と限界を記録する。
- データとAPIでは期限、権限、再送、順序、退出との競合、保存削除を確認する。
- リンク切れ、古い版番号、現行文書間の矛盾、未決定なのに決定として書かれた箇所を点検する。
- docsの正しさをリンク検査だけで証明したとしない。会話の根拠と実装事実の照合が必要。

## 検証を選ぶ基準（2026-10-29 ユーザー指定）

ビルド・テストの反復によるトークンと時間の消費を抑える。作業ごとに次を判断し、必要な範囲だけ実行する。

1. 変更した責務と関連R番号、修正対象の失敗を特定する。
2. 既存の成功結果が引き続き有効な範囲を確認する。
3. 対象の不具合を検出できる最小の検証を選ぶ。通信・DB・実機固有の問題を、型チェックだけで確認済みにしない。
4. 再実行は関連コード・依存・設定・環境が変わった場合、試験失敗、または新しい懸念が出た場合に限る。無関係な文書修正ではビルドしない。
5. ネイティブビルド・実機転送は変更をまとめてから行い、目的と結果・残る未確認を記録する。必須チェックは守り、同じ版に対する不要な反復はしない。

この方針は検証の全省略を意味しない。直したかった不具合を見逃さないことを優先しつつ、検証の範囲と回数を絞る。
