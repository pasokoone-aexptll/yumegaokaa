# データモデル設計レビュー v0.1

2026-10-29。[対象](DATA_MODEL_AND_STATES.md)。会話の合意、要件、異常時の処理順、PostgreSQL/Supabaseの公式仕様を照合。**実装脆弱性の発見・侵入試験・実DBテストではなく設計レビュー。** 問題なしとは判断しない。基盤を変更する根拠は今のところないが、下記は実装前に補強が必要。

D01（1滞在1更新端末、自動移行なし）はユーザー承認済み。後続で入退場例外5項目とD03も承認済み。D04・D05は後続で承認済み。以下の具体方式とD02は未承認。重要度「高」は、当該処理の実装前に解決するという意味。

## F01 高：入街処理中の退出が遅延した成功で覆される

再現：開始要求を送る→応答が途絶える→本人がOFF/キャンセル→visit_idがまだ不明→サーバーで開始確定→古い成功応答を受けてONに戻る。現行図のUncertainには取消経路がなく、visit_idだけの退出APIでは未確定の開始を止められない。

修正案：開始試行を識別するattempt_idと状態（pending/committed/cancelled）を持ち、取消をそのIDで受ける。開始と取消を同じ試行で直列化する。開始が先なら関連visitを終了、取消が先なら開始を拒否。端末の操作世代も保持し、取消以前の成功応答ではONへ戻さない。通信断時はサーバーの反映遅延を説明し、結果不明を「開始失敗」と断定しない。

D02の期限を試行にも適用し、削除済み/受付期限超過の開始要求では作成しない。単にクライアントが新しいrequest_idを付ければ何度も入街できる問題はF07で別に扱う。

## F02 高：更新元端末のID申告だけではD01を守れない

再現：同じアカウントの別端末Bが、Aのvisit_idとwriter_idをリクエストに指定する。所有者が同じだから通す実装だと、更新権限が自動移行しないという合意を破る。

修正案：サーバーが確認した認証セッションとの結合、またはその端末だけが保持する更新用資格情報で検証する。第一候補は署名検証済みJWTのsession_idを開始時に結び付ける方法。ただしsession_idは端末ハードウェアIDではなく、同じ端末で再ログインすると別セッションになり得る。認証情報のコピーによる物理端末判別も保証しない。通常のトークン更新で継続できるか、ログアウト・再認証時の扱いを実装前に決める。

Supabaseのセッション識別は公式に存在するが、JWTの有効性だけでサインアウトの即時反映を保証しない。端末紛失・資格失効・終了操作を受ける権限は、位置更新の権限と区別して設計する。[セッション仕様](https://supabase.com/docs/guides/auth/sessions)

## F03 高：利用停止をDBに書くだけではRealtime購読が止まらない

再現：有資格でチャットを購読→運営が停止→APIは拒否するが、既存Broadcast接続は新しい本文を受信し続ける。公式には接続の権限がキャッシュされ、JWT更新/失効等まで配信が続き得る。[Realtime権限](https://supabase.com/docs/guides/realtime/authorization)

修正案：private channelだけで停止対応完了としない。第一候補は本文・区画・ユーザーIDを含まない変更通知と、取得時に資格を検証するAPIの組合せ。停止後も通知のタイミングは届き得る。通知も止める要件なら、サーバー側の強制遮断またはチャンネル世代切替等を別途設計・検証する。クライアントへの「切断して」通知だけは強制にならない。

チャット本文直接配信の可否、停止反映の許容時間はQ02/Q09。既に端末が取得した内容を回収できるとは説明しない。

## F04 高：イベント行をロックするだけでは、定員集計の鮮度を保証しない

再現候補：残席1。Aが親eventをロックし登録→BがAの確定前に開始した同じSQL文/古いスナップショットで人数を読む→ロックを待っても古い人数で登録する。関数呼出し1回という説明だけではSQL内の読み取り時点が決まらない。

修正案：Read Committedを前提に、親ロック取得後の別のSQLステートメントで人数を再取得し、参加・取消・定員変更の全経路を同じ親ロックへ統一する案。関数のvolatility・内部SQL・分離レベルを確認する。別案は定員を含む親行の条件付き更新またはSerializableと競合再試行。方式を混在させず、2接続を意図的に待機させるDB試験で確認する。[分離レベル](https://www.postgresql.org/docs/current/transaction-iso.html)

同じ注意は募集1件制限、招待発行枠、イベント3件制限にも当てはまる。通常処理で共有ロックを取った後に同じ行を排他へ昇格する設計は相互待ちを生み得るため、処理ごとに必要モードを最初から決める。

## F05 高：サーバーが正しくても古い応答でUIが巻き戻る

再現：気配更新の成功応答を遅延→退出成功を受信してOFF→古い更新応答が届いてON。街のスナップショットも、新しい結果の後に古い結果を描画すると前の区画に気配が戻る。visitの観測番号だけでは退出・取得結果の順序を扱えない。

修正案：端末の操作世代、対象visit_id、サーバーの状態版を照合し、古い応答を破棄する。公開データには個人の更新番号を渡さず、街/公開スナップショットの版または取得世代を用いる。時計だけで順序を決めない。初期取得と購読開始の隙間は、購読確立後の再取得等で埋める。再接続時の再取得だけでなく、通知欠落や書込確定後の配信失敗に対する回復取得も必要。

これはR06/R07/R08/R15のクライアント側確認条件を補うもので、個人識別子の公開を追加するものではない。

## F06 中：関連IDを独立に保存すると、別の街・所有者のデータを結合できる

presenceがvisit_idとstreet_idを別々に保持し、単独の外部キーしかなければ「街Aの滞在なのに街Bへ気配」の組合せを表現できる。募集のownerとvisitのowner、区画IDと区画定義版も同様。

修正案：街/所有者は親から導出するか、冗長に持つ場合は複合外部キー・制約で組を保証する。入力時だけでなくDBでも破れない構造にする。イベント定員・開始終了・募集期限等の基本制約もDDLで明示する。安易な全CASCADEは保持期限の異なる入街ログ・通報証拠と衝突する。

区画定義の版が変わったとき、古い気配を新しい同名区画へ読み替えない。街範囲版と区画定義版は分け、旧気配が失効するまでの表示をQ05で決める。範囲変更だけで全員退出させない合意は維持する。

## F07 中：同じ端末が再タッチした場合の重複滞在が未定義

同じrequest_idの再送を防いでも、再タッチや画面の作り直しで新しいrequest_idを発行すると、同じ端末・同じ街に滞在が2件でき得る。D01は1滞在の更新元を制限するだけで、滞在の生成数を制限しない。

提案：同じ更新元・同じ街の有効滞在がある場合は既存状態を返して人数・入街ログを増やさない。後続合意で、同端末の再タッチは既存状態を返し、新端末での再NFCは旧滞在・旧募集を終了して切り替えることが決定。具体方式は未実装。複数端末の意図的水増し対策を新たに追加する要求ではない。Q04へ追加。

## 追加の設計ゲート

- 期限付き再送のD02は、受付期限をクライアントが自由に書き換えられない仕組みが必要。期限内に始まった処理がロック待ち中に重複記録削除を追い越さないよう、処理直前の期限確認と清掃も整合させる。
- DB関数は新規作成時のPUBLIC実行権に注意し、作成と権限制限を同じマイグレーションで行う。RLSの有効化だけで関数呼出しを保護したとしない。[PostgreSQL関数権限](https://www.postgresql.org/docs/current/sql-createfunction.html)
- 全リクエスト本文・区画のハッシュを重複対策として蓄積しない。バックアップ・配信履歴・外部ログまで含めた保存期限は未解決。
- 「街内判定を端末に任せる」A案の限界は残る。位置偽装を完全に防ぐ設計への無断変更はしない。
