# 審査アクセスの設計・メモ草案

2026-11-25。C04／T031/T033／R03〜R09。ユーザーは独立した審査用デモの**設計**を承認。実装・Apple了承・審査アカウント作成は未完。

## 現在の制約

メールOTP→招待QR→表示名／プロフィール画像→街pool画像の登録が通常導線（useAccountAccess）。入街には現地NFC・測位が必要。一般アカウントの認証を固定OTPで迂回しない。UI_REVIEWのSimulator fixtureやFIELD_TRIALの本人限定タグを審査デモへ流用しない。

[Apple 2.1](https://developer.apple.com/app-store/review/guidelines/#app-completeness)は、アカウントが必要な場合のアクセス提供を求める。法的・セキュリティ上の理由でアカウントを提供できない場合の内蔵デモには事前承認の条件がある。本件の現地NFC制約が自動的にこの例外に該当するとは判断しない。審査用アカウントを用意する方針を維持し、地域制限部分の補助手段をAppleへ相談する。

## 提案する構成（未実装）

1. 通常認証を通した審査専用アカウントを用意。資格はサーバー側で付与し、公開バイナリにパスワード・固定OTP・共通秘密を埋め込まない。
2. 本番と分離した審査用データ環境に架空の街・会員・PIN・チャットを準備。通常ユーザーの現在地、投稿、画像を使わない。
3. 審査用アカウントだけが明示されたデモ範囲を利用。画面にデモであることを示し、NFC読取と位置変化のどの部分を代替するのかを審査メモへ記載。
4. 代替するのは現地入力のみ。権限拒否、状態遷移、投稿、通報、ブロック、退会は実APIで動かす。別権限で本番へ戻れないことと、公開アカウントがデモを呼べないことをサーバーで検証する。
5. 退会試験後に使用できる予備アカウントと招待を用意。審査中に失効しない運用、バックエンド監視、問い合わせへの対応を決める。

費用を伴う別環境、体験が変わるデモ導線、具体的なOTP受取方法は実装前の判断点。ブラウザへ誰でも閲覧可能なOTP受信箱を公開する案は採用しない。審査員のメールを本人操作で登録できる招待方式、管理されたテストメール受信方法などを比較する。現地機能の実機動画は補足資料であり、操作可能なアプリの代替としない。

### 認証と導線

公開バイナリにも審査用アクセスの入口と説明を明示し、Appleに審査メモで知らせる。隠しタップや一般認証の固定OTPは使わない。審査環境への切替時は通常セッション、購読、通知登録、画像・街キャッシュを破棄し、ログイン前に接続先を固定する。一般のアカウントや本番JWTを審査環境へ転送しない。

ログイン候補は、(A)審査用環境だけで発行する通常のメール＋パスワードのテストアカウント、(B)審査員本人のメールへ通常OTPと審査用招待を送る方式。推奨AはApp Store Connectの審査情報欄に資格を渡し、リポジトリやバイナリへ保存しない。通常利用者のメールOTPは変更しない。Aは追加UIと審査Auth設定、Bはメール到着・招待再発行・審査員自身の登録作業の確実性が課題。どちらも実装前に本人判断が必要。

### 実装単位と受入

1. 別環境に本番と同じmigrationを適用。架空の街・画像・会員・PIN・チャットのみseed。本番DBのコピーは禁止。seedは接続先allowlistと非本番project IDの二重検査、秘密情報なし、再実行で重複しない構成にする。
2. mobileのAPI/Storage/realtime設定を1つの環境オブジェクトで切り替える。全native観測設定も同じ境界に接続。環境切替とlogoutのキャッシュ消去を試験する。
3. 審査サーバーに限定した審査資格を通常ログイン後に確認。NFC入力の代替・区画変更・退出だけを明示デモ操作として追加し、通常の状態遷移と読取/投稿/通報/削除は共通APIを使う。デモ操作は本番側へ配備しない。
4. 本番宛gateway/Storage/pushへ到達しない接続設定とネットワーク確認を行う。架空の参加者へ実APNsを送らない。NFC/背景位置/APNsそのものの実機確認は別で必要。
5. デモの削除は本当の削除処理を使う。審査用予備アカウントと再準備手順を作る。全データを自動で無差別初期化する方式は採らない。
6. 提出版で新規ログイン→再ログイン→PIN/チャット→通報/ブロック→退出→退会を実施。非審査資格のデモ操作拒否、本番と審査の相互JWT拒否、キャッシュ漏れなしを確認。
