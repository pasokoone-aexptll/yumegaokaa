# MVPの残りの詳細：推奨案 v0.1

作成日：2026-10-28。**この文書の案・数値・技術選定はすべて未承認。** ユーザーの選択後に要件へ反映する。合意済み事項は [MVP_REQUIREMENTS.md](../MVP_REQUIREMENTS.md) を参照。

## P01：招待前の公開範囲

最初は登録済みの招待参加者だけが街の内容を閲覧できる案を推奨。招待リンクの案内画面は公開するが、人数・ピン・チャット本文は非公開。街へのインが不要という合意とは両立する。

理由：小規模な実験で公開範囲が理解しやすい。外部への拡散は紹介・招待で開始できる。将来の一般公開とは別判断。招待参加者による転載・保存は防げない。

## P02：登録・認証・紛失時復旧

利用者は「招待を受け取る → 名前・アイコンを設定」で開始し、実名・電話番号・メールを初期必須にしない案を推奨。端末に安全に保持する認証資格情報と、サーバーの安定したアカウントIDを分ける。名前を本人確認に使わない。暗号方式を独自に発明せず、実績のある認証方式・ライブラリを選定する。

通常の引き継ぎは合意済みQR。復旧用には、別途保存できる一回限りの回復コードを候補とする。端末もコードも失った場合は新規招待で作り直す方針を提案。運営が名前の一致だけで旧アカウントを渡さない。コードの紛失・盗難と利用者の保管負担が欠点なので、メール復旧を希望するかはユーザー判断。

QRの有効期限は仮に2分。QRは移行要求に紐付け、引き継ぎ先の確認表示と旧端末承認を行う。移行完了時は旧セッションと古い資格情報を失効。途中失敗時に両端末が使えなくならない手順とする。新端末に有効チェックインを引き継ぐかは、まず引き継がず再NFCとする案（参加の重複を避けやすい）。

運営にはより強い認証と再認証を設ける。一般利用者へ配布するアプリ内の値だけで運営権限を判定しない。

## P03：位置確認と期限

最初のMVPはアプリを開いた／前面に戻したときの位置確認を基本とし、バックグラウンド更新は後続候補にする案を推奨。使用中の位置許可から始められる。ユーザーのバックグラウンド更新希望を撤回扱いにはせず、優先順位の提案として確認する。欠点は3時間アプリを開かないと現地でも失効し、再NFCが必要なこと。

- サーバーが更新を受理した時刻から3時間有効。端末時計や「元の期限＋3時間」にしない。
- 期限が切れた滞在は延長しない。古い更新を受理して復活させない。
- 使用中も一定間隔で確認する案（仮に15分）。切替連打などによる連続測位を避ける。間隔は電池・実測に基づき調整。
- 街内と判断できた場合だけ延長。明確に圏外ならアウト。
- 測位不能・低精度・権限拒否・通信失敗は「不明」とし、元の期限を維持。自動再参加しない。
- 最新の街範囲を取得できない場合は更新を保留。座標は端末内で判定し、サーバーには更新要求と範囲の版等のみを送る。
- 位置許可を拒否しても街の閲覧・チャットは利用可能。募集ピンには測位が必要。
- オフラインで手動退出した場合は端末で退出意思を即記録し自動更新を止め、再接続時に終了通知を再送。サーバーへの反映は再接続または期限まで遅れると表示する。

端末判定だけでは改造端末による虚偽更新を防げない。人数の目安という目的から、GPS座標を収集しないこととのトレードオフとして受け入れるか決める。

## P04：街の外周とステッカー運用

登録点の凸包（全点を囲む最小の凸多角形）を最初の外周算出候補とする。外側の点を結ぶという合意を単純に表現できる。ただし飛び地を含めると間の広い空白も街になり、凹んだ境界は表せない。範囲プレビューを確定前に必ず確認する案。

境界付近はGPS精度を考慮して「街内／街外／不明」に分ける。許容幅は実地で決め、700mなど過去の値を流用しない。3点以上でも一直線・同一地点では範囲が成立しないため検証する。

タグIDと設置位置を分離。移設・交換・撤去を管理し、作業中は当該タグの新規利用を停止する案。旧タグを無効化し、位置とエリアを版付きで一括公開。複数地点をまとめて変更できる。運営画面はスマホから位置登録できるレスポンシブWebを第一候補とする。実際のNFC書き込みをWeb内で完結させることは前提にせず、タグ準備・読み取りとの連携は別途検証する。

通常の固定NFCはコピー可能。最初は失効・再発行・招待と頻度制限を使う案。暗号対応タグの採否は、機材・不正耐性を比較して決める。タグIDそのものを秘密の認証情報と扱わない。

## P05：投稿・招待の具体的な初期上限

以下は小規模試験向けの調整可能な出発値であり、実測に裏付けられた最適値ではない。上限はサーバーで強制する。

| 項目 | 提案値 |
| --- | --- |
| 招待 | 1コード1回、7日有効、各参加者の新規発行は7日間に5件まで。運営が追加・停止可能 |
| チャット | 本文500文字、1人あたり10秒に5件かつ1分に20件まで |
| 履歴 | 1回50件、1アカウントあたり10秒に5回まで |
| 募集ピン | 同時1件。編集で20分の期限を伸ばさない |
| ピン作成全体 | 1人あたり1分に3件まで。削除・再作成の繰り返しにも適用 |
| オフ会ピン | 同時に掲載する予定は3件まで。開始は90日先まで、開催期間は最大24時間 |
| ピン題名・説明 | 題名50文字、説明1,000文字まで |
| リアルタイム接続 | 1端末原則1本、1アカウント3本まで。再接続の一時重複は許容 |
| アイコン | 画像のみ、最大2MB、サーバー側で縮小・再エンコードして位置等のメタデータを除去 |

同一IPは店のWi-Fiなどで共有されるため、IPは補助制御とし、少人数分の上限で全員を止めない。全体負荷上限は試験規模・インフラに合わせて設定。運営による制限値変更と、拒否時に待ち時間を示すUIを検討する。

## P06：ピン・チャットの細部

- オフ会は未チェックインでも作成。開始・終了日時、題名、位置を必須、説明は任意。開始後は「開催中」、終了後は非表示。
- 募集は公開前に地図と公開位置を確認する。本人が動いても座標は動かさない。「募集した場所」であることを表示。
- 募集の題名は編集可能、位置変更は終了して再作成とする案。終了済みを編集で復活させない。
- 本人が自分のチャットを削除可能。運営も削除できる。運営が他者の本文を書き換える機能は設けず、削除と説明を使う案。
- チャットはテキストのみ。画像・動画添付は最初に含めない。
- 再送時の重複表示を防ぎ、再接続で取得可能な範囲の欠落を補完する。通常履歴30日より古いものを復元する機能にはしない。
- 個人ブロックを追加候補とする。ブロックは自分の表示を抑制するもので、公開位置を相手から確実に隠す手段とは約束しない。

## P07：データの保持・削除

通常チャット30日は合意済み。以下の追加期間は提案。公開終了と物理削除、バックアップ残存を混同しない。

| データ | 提案する扱い |
| --- | --- |
| 通常チャット | 30日を超えたら取得対象外。削除処理は24時間以内に実行する案 |
| 終了したピンの本文・座標 | 終了後は取得対象外、24時間以内に削除。通報対象の最小証拠は別管理 |
| 終了した滞在 | 位置履歴は持たない。再送の判定に必要な最小の終了情報を24時間後に削除する案 |
| 通報証拠 | 運営限定。対応完了後30日で削除、未対応90日で運営に整理を要求。無期限保管しない規則を別途確定 |
| セキュリティログ | 原則7日。本文・位置・認証トークンを記録しない |
| 運営操作記録 | 90日。誰が何を制限したか等を記録し、本文の複製を避ける |
| バックアップ | 原則7日。選んだサービスで実現可能か確認し、削除後の最大残存期間を明示 |
| 招待関係 | 監督のためアカウント有効中は保持する案。退会後の扱いは別途決定 |

失効した記録を物理削除しても、古い更新を新規チェックインとして扱わない。バックアップ復元時は削除・期限・停止状態を再適用してからサービスを再開する。IP等を収集する場合は目的と期間を限定する。

アカウント削除も追加候補として設計する。削除後に残す制限・通報の最小情報と、名前・アイコン・投稿の削除範囲はユーザーに明示する。

## P08：技術構成の第一候補

以下は比較の出発点で、導入・契約・費用支出の承認ではない。

- 利用者アプリ：React Native＋TypeScript＋Expo Development Build。両OSのUIを共有し、NFC等のネイティブ機能は開発ビルドで実機確認。Expo Goで全機能が動く前提にしない。
- 運営：スマホでも使えるReact製Web画面。専用ネイティブアプリを最初から二つ増やさず、招待・通報・位置登録をまとめる。
- バックエンド：単一のAPIとPostgreSQLを軸にする。認証、権限、期限判定、再送制御はここで管理。マイクロサービス分割は初期に行わない。
- 配信・ホスティング候補：Supabase等の管理型基盤を比較。SupabaseにはRLSとリアルタイム配信があるが、権限設計・負荷制御・失効処理を自動で満たすわけではない。匿名アカウント認証とQR・復旧の整合も選定前に検証。
- 地図：MapLibre React Nativeを評価候補とする。地図データ・タイル配信元、利用条件、料金、表示品質は別途選ぶ。レンダラー採用だけでは地図データの調達まで完了しない。
- 見た目：最初は地理的に正しい地図と独自のピン・配色・アニメーションを作る案。添付のイラスト調3Dの街をどこまで再現するかは独立した製品判断。勝手に2Dへ変更しない。

バックエンドの配置地域・価格・監視とバックアップは試験規模と保存方針が決まってから比較する。現在は性能・費用の保証をしていない。

## P09：初回公開と完了条件

最初は池袋の一つの街、招待参加者10〜20人程度でのオフ会を試験案とする。両OSを対象にし、ストア本公開の前に両OSのテスト配布で現地確認を行う案。配布方式・公開順は未決定。

仮の性能目標：同時接続50、街全体で毎秒5件のチャットを10分間送信する試験で、安定したネットワーク下のサーバー受理から接続済み端末表示までp95で1秒以内。試験条件・計測方法と予算に合わせて合意する。モバイル回線の通信断を1秒以内で解消する保証ではない。

公開前の完了条件案：

1. 要件定義の確認項目が両OS実機で通る。特にNFC、位置拒否、電源断後の失効、手動退出、ピン終了、QR失敗と再試行。
2. 他人の編集削除・運営操作・無資格の募集を拒否する。上限と停止がWebSocket等の既存接続にも反映される。
3. 街範囲の変更を検証し、運営が通報・招待管理を実際に操作できる。
4. ログに本文・秘密情報・不要な位置が出ない。保持期限による削除と復元時の再適用を確認する。
5. 現地で招待からオフ会ピン、NFC、募集、チャット、退出まで一連の動作を確認し、利用を阻害する不具合を解消する。
6. ユーザーが実地利用の準備と公開範囲を承認する。

文化の成功は技術テストと別に扱う。初回は「予定ピンを見て来られる」「募集場所へ合流できる」「人数と会話から街の様子がわかる」を観察する。継続GPS追跡や追加インタビューを開発開始条件にはしない。
