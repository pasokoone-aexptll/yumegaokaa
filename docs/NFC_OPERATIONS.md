# ステッカー登録・設置・移設 詳細設計案 v0.1

2026-10-29。対象R04/R11/R18/R17。運営はiPhoneでNFC基本設定を書き込む。3か所以上の設置位置の凸包を街の範囲とし、変更だけで全員を退出させないことは承認済み。N01〜N03は承認済み。具体的なデータ・API・機種等は設計案。運営ワークフローは準備・照合・設置・凸包公開・移設/停止・下書き編集/取消をローカルDBと画面へ接続中。交換時の旧新タグ原子公開もDB試験済み。全画面一巡は未確認。実タグ試験は未実施。開発用の物理NFC代用を実タグ成功とは扱わない。ライブラリはK01でreact-native-nfc-managerを採用済み。

## 運営の画面と手順

一覧→新規登録→街・管理名・設置場所入力→NFC書込み→再読取照合→現地設置確認→変更後の街範囲プレビュー→公開。

位置取得は入力補助とし、運営が地図で実際の貼付地点を確認・修正する。これは本人の気配座標の保存禁止とは別の、公共の設備位置登録である。写真を必須にする案は追加していない。

**N01（承認済み）：書込み・再読取・設置確認を終えてから有効化する案。** 電波の届かない場所でも準備状況は表示できるが、サーバーで確定できるまでチェックイン用としては公開しない。初期3枚はまとめて準備し、有効な外周ができた時点で一括公開する。

NFC操作ではiOS標準の読み書き画面が入る。アプリ独自の進捗表示はその前後に配置し、書込み完了前に成功演出を出さない。Core NFCにはNDEF書込みと書込み可否・容量照会がある。実タグとライブラリの適合確認は別途行う。[Apple writeNDEF](https://developer.apple.com/documentation/corenfc/nfcndeftag/writendef%28_%3Acompletionhandler%3A%29)

## タグとサーバーの役割

**N02（承認済み）：タグには書式版と推測困難なtag_idを記録し、場所と街はサーバーで管理する案。** 個人名・滞在トークン・運営権限・現在の設置座標は書き込まない。移設時は同じタグを再読取して、新しい設置情報を登録できる。書式はNDEFのアプリ用レコードを第一候補とし、URL方式・ドメイン・ライブラリ・機種は未選定。

通常の読取でサーバーから現在の街・設置版・有効状態を得る。端末が送るstreet_idや古いタグ内座標を信用しない。タグ複製では同じIDがコピーされるため、ランダムIDだけで複製防止になるとは扱わない。書込みロックは不可逆の場合があるため、自動で実行せず機種・保護方針の決定後に扱う。

## データ案

| データ | 主な項目 |
| --- | --- |
| tags | tag_id、payload_version、管理名、draft/verified/active/suspended/retired、revision |
| placements | placement_id、tag_id、street_id、座標、設置確認時刻、版、現行か否か |
| provisioning_operations | operation_id、操作者、対象tag、expected_revision、書込予定内容の照合値、進捗、結果。利用者情報を含めない |
| area_versions | street_id、版、構成する設置ID一覧、境界、作成者、公開時刻。公開後不変 |
| street_config_drafts | 基準となる街版、追加・移設・撤去の候補、プレビュー。公開中設定と分離 |

権限はサーバーで運営資格を毎回確認。UIを隠すだけで済ませない。監査は既存の90日方針に沿い、操作ID・対象・変更種別を記録する。未完了登録下書きは最終更新から7日で削除する（M05）。運営操作はTOTP/MFAを必須とする（M03）。タグの物理UIDをセキュリティ上の秘密や単独の真正性証明として使わない。

## 状態・失敗時の扱い

- draft：まだチェックイン不可。書込み前後でDBが有効にならない。
- verified：書込内容を再読取して照合した準備済み状態。設置・範囲公開前なのでチェックイン不可。
- active：現在の公開設置に対応。初めてチェックイン可能。
- suspended：新規チェックイン不可。移設中・紛失・破損等。復帰は状態と版を再検査。
- retired：交換済み・廃止。古い要求で再有効化しない。

物理タグへの書込みとDB処理は一つのトランザクションにはならない。書込み後に通信断なら未確認として保持し、復旧後に同じoperationを照会して再読取から再開する。書込み失敗・照合不一致なら有効化しない。別タグに同じpayloadを再試行して複製しないよう、再開時に対象タグと操作を確認し、不確実なら旧IDを廃止して新規登録する。

有効化はoperation_idで冪等にし、タグ版・公開街版の一致を確認する。応答紛失時は再公開せず結果照会。別の運営操作が先に確定していればプレビューを作り直す。

## 移設・交換・撤去

移設：対象タグを一時停止→現物を移動→新しい場所で再読取・位置確認→新範囲プレビュー→設置版と範囲版を同時公開して再有効化。移設中は旧公開範囲を保持する案。旧版で発行済みの未確定チェックインもcommit時に現行タグ状態・設置版を再検査し、停止・移設を跨いで成立させない。

交換：新タグの準備と設置確認→新タグ有効化と旧タグ廃止を同じDB処理で確定。旧IDは再利用しない。旧タグが紛失・漏洩している場合は新タグを待たず先に停止できる。

撤去：タグを停止して新規チェックインを止める→残る設置から外周をプレビュー→範囲を公開。範囲の変更によって既存滞在を一斉終了しない。次の観測で最新範囲を適用する。

**N03（承認済み）：地点不足・重複・一直線で有効な外周が作れない場合、新範囲は公開せず旧範囲を保持する案。** タグの停止自体は妨げない。代替地点を追加して外周を再構成する。初回で旧範囲がない場合は街のチェックイン受付を開始しない。範囲が一時的に最新の稼働ステッカーだけの凸包と一致しなくなるため、運営画面に未反映を明示する。この例外はN03として承認済み。

## 同時処理と確認ケース

運営資格→街設定→タグ（複数はID順）の共通ロック順で、公開版・タグ有効化・設置変更を一体にする。通常のチェックインは既存のアカウント親→街→タグの順と整合させる。運営操作から利用者全員のアカウントロックを取りに行かない。

未実行ケース：書込不可／容量不足／複数タグ／途中切断／照合不一致で有効化なし。サーバー確定後の応答紛失は同じ結果。移設中の古いcommitは拒否。無効タグで新規チェックイン不可。一般利用者からの登録・公開API直呼びは拒否。2端末同時編集は版不一致。地点不足でも緊急停止可能。公開範囲変更だけでは既存気配・滞在を消さない。

N01〜N03は承認済み。タグ製品・保護・アプリ内運営画面の置き場所、具体API型の設計を残す。購入・書込みロックは別判断。運営フローはMVP_TASKSのT026/T027、実NFCはT028へ分離する。監査後の自律実装を進める。
