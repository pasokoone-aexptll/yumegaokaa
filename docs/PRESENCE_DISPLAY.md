# 気配の公開・描画 詳細設計案 v0.1

2026-10-29。対象R07/R08/R10/R19/R21。Figmaの見た目を基準とする。要件の正本は [MVP_REQUIREMENTS](MVP_REQUIREMENTS.md)。以下は内部処理の設計案。V01〜V03は承認済み。人物推測リスクへの追加対策はMVP後に再検討する。製品コード・集約APIは部分実装。個別期限・分割の試験結果はTECH_VALIDATION。

## 表示の原則

- チャットでは本人、地図では流動的な街アイコン。個人プロフィールへの導線や個人IDを気配に付けない。
- 有効な気配だけを区画単位で数える。ヘッダーの有効チェックイン人数とは別で、不一致は正常。
- 6人まで一まとまり、7人は同じ観測場所の周囲で5＋2。分割は画面上のオフセットであり地理座標を別街区へ移さない。
- 期限は各観測に従う。一人の更新で同区画の他人を延命しない。移動は旧区画から除いて新区画へ追加し、全体で一人分。
- 気配のない地図を「人がいない」と断定しない。未取得／通信断と、取得に成功して気配0件を区別する。

## 公開API案

内部のpresence_currentは非公開。招待資格を確認した集約取得で、street_id、grid_version、server_time、区画ごとのcountと失効予定を返す。募集・イベント・チャットとは別のペイロードにする。

フェードを端末で連続描画し、通信が途切れても期限で消せるよう、区画ごとに `expiry_groups: [{ expires_at, count }]` を返す案。同じ失効時刻の観測は合算する。アカウント、visit、更新順序、writer、個人アイコンキー、正確な観測座標は返さない。更新のたびに最新スナップショットで置換し、観測履歴として保存しない。

**V01 承認済み：区画別の人数と失効予定を返す。** 個人IDはなくても、人数の少ない区画では失効時刻や出入りの相関から個人を推測され得る。完全匿名とは説明しない。代案はサーバーで人数・透明度だけを集約し頻繁に取り直す方式だが、通信断時の個別失効と滑らかなフェードに追加処理が必要。時刻丸めは10分より早く消す／遅く残す可能性があるため無断で採用しない。

各観測の期限が観測時刻＋600秒であることを利用し、期限eに属する人数nの各表示要素の透明度は `clamp((e - estimated_server_time) / 600, 0, 1)` とする案。期限到達で人数から除外する。従来案は街アイコンを表示枠へ付ける方式だったが、2026-10-30の「自分のアイコンをpoolから選び日ごとにシャッフルする」指示により、当日の本人向け割当を保持し地図にも同じ画像を出す方式へ変更する（2026-10-30承認）。既存の人数集約APIを個人識別APIへ無断変更しない。受信遅延分も時間を進め、受信時から10分を数え直さない。時計補正はQ03の共通方式を使う。

合計人数のラベルは残る人の人数へ更新する。複数アイコンをそれぞれ薄くし、まとまり全体を最新の一人に合わせて不透明へ戻さない。7→6などでまとまりを組み直しても失効時刻は持ち越す。描画用の枠番号はローカルだけで利用し、人物を示すIDとしない。

## 分割・配置案

**V02 承認済み：残人数が6以下になるまで5人ずつ切り分ける。** 8→5＋3、9→5＋4、10→5＋5、11→5＋6、12→5＋5＋2。7→5＋2、6→6という合意を一般化する。合計を増減させない。巨大な人数で大量の表示枠が必要になる場合の縮約は別途検討し、無断で架空人数を付けない。

アンカーは固定区画の代表点とし、画面上の小さなオフセットで分割表示。ズームや回転でも街区を移動した意味にならないよう地理アンカーとの関係を保つ。区画が街外周を跨ぐ場合の代表点は、区画と対象範囲の交差領域内に置く計算案。旧範囲で受理済みの気配は新範囲へ無断再配置しないため、受理時の範囲版を内部で保持する案が必要。この内部案はFIRST_SLICE_CONTRACTのpresence.area_versionと公開集約キーへ具体化した。集約キーと代表点のコードは実装済み。既存の計算/DB試験と描画確認の範囲はMVP_IMPLEMENTATION_AUDITのE05/E07。Figmaとの全体一致や複数閲覧端末の確認は残る。

**V03 更新：登録時に利用者が提供する街pool画像を使用する（2026-10-30の明示訂正）。** アカウント作成時にpool用画像を必須でアップロードし、街へ保存する。地図で自分に表示される画像はpoolから選び、1日ごとにランダムシャッフルする。登録画面で共有用途を説明する。従来の運営素材限定方式は置換。チャット本人画像は別設定。当日の割当を本人が確認でき、地図にも同じ画像を出す。日替わりは日本時間午前0時。提供者の差し替え・削除・退会でpoolから取り下げる（2026-10-30承認）。公開APIへ名前や個人IDは追加しない。Figmaの丸い画像表現は維持し、画像切替を新規人数や新観測と扱わない。

## 取得・更新の順序

1. 街の購読を確立してからスナップショット取得。取得中に更新通知が来たら完了後に再取得。
2. 通知は変更ありの合図のみ。個人行を直接配信しない。
3. 同一街の取得は一つずつ実行し、操作世代が変わった旧応答を破棄。別街の応答を混ぜない。
4. 復帰・再接続時に再取得。通知取りこぼし対策として表示中は30秒ごとの再取得を初期実装候補とする。性能目標を満たす実測は別。
5. 取得済みの期限は端末でも進める。通信断は表示し、更新できなくても古い気配を延命しない。認証・資格失効を検出したら表示を破棄する。

取得時点の合計とexpiry_groupsの合計を一致させる。一つのDBスナップショットで滞在有効性と気配期限を検査する。初期MVPでは街全体の小規模スナップショットを基本とし、ページを跨いで移動前後を二重計上する設計を避ける。既存購読への利用停止反映はQ09の課題として残る。

## 確認ケース（未実行）

- 2人の片方だけ更新：更新していない側だけ10分で消え、人数は1。
- AからBへ移動：同じスナップショットでA−1、B＋1、総数不変。
- 7→6、12→11：分割合計と失効予定を維持。
- 全員失効／通信断／別街切替：古い表示を残したり旧応答で復活させたりしない。
- 公開応答に個人ID・プロフィール参照・生座標がない。時刻相関の残余リスクを説明する。
- 旧範囲の気配は範囲変更だけで消失・新しい場所への移動をしない。
