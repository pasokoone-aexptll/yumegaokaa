# 街ローカルチャット・通報・制限 詳細設計案 v0.1

2026-10-29。対象R03/R15/R16/R17/R18/R19。要件7〜9章が正本。C01〜C03は承認済み。他の未確定事項は提案。製品コード・DB試験は未実施。

## 1. 体験と画面

FigmaのMap下部に街チャットを表示。閲覧・投稿に現地チェックインを要求しない。名前と本人アイコンで発言者を識別する。地図の流動的アイコンをチャットへ流用しない。

過去へスクロールするとチャットを拡大し背景をぼかす。過去を読んでいる最中に新着へ強制スクロールせず、新着ありの操作で戻る案。入力は画面の拡大・縮小で維持。投稿・ピン作成を求めず眺めているだけでも気配を感じられるMapを維持する。

送信中・失敗・再試行を本人の端末内で区別。成功確定前のメッセージを他人へ配信しない。再試行で重複投稿しない。受信者ごとに名前が変わる匿名チャットにはしない。

## 2. データと取得

messages：id、street_id、author_id、kind(text/arrival)、body（textのみ）、created_at、deleted_at、revision。arrivalは新規visit開始処理と一体で生成し同じvisitにつき一回だけ。更新・既存滞在の再NFCでは生成しない。visitの24時間削除を妨げない最小の重複識別とし、ログから非公開気配へ辿るAPIを作らない。

プロフィールは現在の表示名・本人画像への参照を基本案とする。**過去投稿にも現在プロフィールを表示する（M01承認済み）**で、画像履歴を無断保存しない。本文の編集はMVP要件にないため追加しない。本人と運営は削除できるが、運営が本文を書き換える操作は作らない。

過去履歴はcreated_at＋idのキーセットカーソルで50件ずつ。サーバー時刻で30日を超えた行を除外。最新取得と購読の間の取りこぼしは再取得・ID重複除去で回復。欠落修復を単なる最新50件だけで済ませず、切断後の差分をページ取得する。古い端末応答で削除された内容を復活させない。

公開取得は招待資格と制限を毎回確認。投稿には500文字、10秒5件かつ1分20件、履歴取得には10秒5回を適用。文字数の数え方・作成要求の有限受付方式はAPI共通設計で明記する。DB関数で資格・上限検査と投稿を同じ処理にし、再送成功を新しい投稿として数え直さない。

## 3. 名前付き入街ログと削除の合意候補

**C01（承認済み）：入街ログも通常チャットと同じ30日表示、その後24時間以内に削除する案。** 保存ルールを一本化し友人の来訪がチャットで分かる。来訪履歴として残る点は明示する。位置経路を記録する仕様ではない。代案は入街ログだけ24時間等へ短縮するが、別保持ルールとなる。

**C02（承認済み）：削除した投稿は本文を直ちに非表示にし、「削除されたメッセージ」と表示する案。** サーバーの通常本文も削除処理で消去し、ID・街・作成時刻・削除状態等の最小行を元の履歴期限まで保持。空行や順序の飛びを自然に扱い、再送で本文を復活させない。通報済みの必要な証拠は別権限・別期限で保持する。本人削除と運営削除で本文を残す扱いを変えない。

既に他端末が取得した内容の完全回収は保証しない。再取得・削除通知で通常表示とキャッシュを更新し、ログアウト・資格喪失時には街情報のキャッシュを破棄する。バックアップは既存の保存方針に従う。

## 4. ブロック

**C03（承認済み）：ブロックは自分の画面で対象のチャット・入街ログ・募集ピンを非表示にする案。** 本人の操作で解除可能。相手へブロック通知を送らない。サーバーの取得でもフィルターし、プロフィール照会等の別経路と整合させる。

匿名の気配と街人数はブロックで減らさない。気配から特定人を除くための対応を公開しない。ブロックは相手から自分を見えなくする機能や、現実の接近を防ぐ機能ではない。

イベントは主催・参加・重要変更の関係があるため、この提案では自動非表示にしない。イベントを含める場合は「参加中の主催者をブロックした時」等を別に設計する。既存の参加者名公開範囲も変えない。対象データを全部配信してUIだけで隠すことをサーバーフィルターと同等とは扱わない。リアルタイム通知は取得の合図として利用し、対象本文の無条件Broadcastを避ける。

## 5. 通報と運営対応

投稿／募集／イベントの詳細から通報→理由選択と任意説明→受付。同じ対象への重複通報で運営一覧が埋まらないよう、未解決の同一通報者＋対象を統合する案。通報者を対象者へ公開しない。通報数だけで永久停止しない。

reports：id、reporter、target_type/id、理由、限定された証拠、open/in_review/resolved、担当、対応日時。証拠はサーバーが取得できる対象から最小限を取り、利用者が書いた説明を事実認定として扱わない。対象が既に削除済みならその状態で受け付け、消えた本文を創作・復元しない。

運営一覧→対象確認→対応選択→理由確認→確定。操作は運営資格をサーバー検証し、監査90日。証拠は一般履歴・公開Storageに置かない。対応完了後30日削除、未対応90日で整理。未対応通報は最長180日で削除（M05）。

制限は区別する：
- チャット投稿制限：新規投稿を拒否。既存の滞在を終了させない。
- 投稿削除：対象本文を非表示。利用停止と同一視しない。
- 利用停止：利用資格を止め、滞在・気配・募集も終了。解除で滞在を復活させない。

投稿制限は運営指定の終了日時まで、利用停止は運営解除まで継続する（M07）。停止中アカウントの参加の扱い、既存接続失効は後続判断。運営はメールOTP＋TOTP/MFAを必須としサーバーが確認する（M03）。M06により、利用停止された主催者の開催前・開催中イベントは自動中止して参加者へ通知する。解除で復活させない。

## 6. 競合・確認ケース（未実行）

投稿受理と利用停止は資格親のロックで整合。削除と通報証拠取得は対象行のロック順を統一。通報で既に削除された本文を通常履歴へ戻さない。投稿IDと操作IDで応答紛失後の重複を防ぎ、削除後の同じ作成要求は元の削除状態を返す。有限受付期限と記録削除の共通設計D02が前提。

確認：500文字・頻度境界／並列送信／切断中の新着が50件超／送信成功後の応答紛失／削除通知より古い履歴応答／ブロック後の再取得／相手への通報者漏洩／一般ユーザーの運営API直呼び／停止と更新競合／期限後の履歴除外と物理削除。Figmaのチャット拡大でMapへ戻れなくならないことも確認。
